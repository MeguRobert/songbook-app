# Phase 08 Plan 01: Setlist Data Model & Persistence — Summary

**One-liner:** A Setlist is a named, ordered list of song numbers; it persists as a single JSON blob
in the existing local store, and a SetlistRepository exposes create/rename/delete/add/remove/reorder.

## What Was Built

**Setlist model** (`setlist.dart` + `setlist.g.dart`) — immutable, JSON-serializable value object:
`id`, `name`, `List<int> songNumbers` (ordered, `defaultValue: []`), `createdAt`, `updatedAt`. Has
`copyWith`, `length`/`isEmpty` getters, `toString`, and equality keyed on `id` only (consistent with
Song/Favorite identity). The `.g.dart` was hand-written to match the json_serializable generator
output (no network/build_runner dependency).

**Persistence** — `LocalDataSource.getSetlists()/saveSetlists()` store the whole list as one
JSON-encoded string under the `setlists` key, mirroring the favorites storage (silent-fallback to
`[]` on decode error).

**SetlistRepository** — wraps LocalDataSource:
- `getSetlists()`, `getById(id)`
- `createSetlist(name)` → generates `sl_<microseconds>` id, returns the new Setlist
- `renameSetlist`, `deleteSetlist`
- `addSong` (idempotent append), `removeSong` (no-op if absent), `reorderSongs` (exact order)
- a private `_update` helper bumps `updatedAt` and persists; unknown id → `false` (no exceptions).
